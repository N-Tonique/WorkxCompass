# 🔵 RÔLE A — UI / Knowledge Compass
**1 personne**

## Objectif

Construire toute l'interface visible du prototype.

L'utilisateur doit pouvoir sélectionner un contexte métier et voir immédiatement
les connaissances recommandées, leurs scores, leurs sources, les conflits et
l'expert recommandé.

## Tâches

### 1. Structure de l'application

Créer l'interface principale simulant un environnement mySDWorx.

Fichiers principaux :

src/app/page.tsx

src/components/
  knowledge-compass/
  knowledge-card/
  context-selector/

### 2. Context Selector

Créer un sélecteur permettant de choisir entre :

- Belgium / Payroll / Bonus
- France / Payroll / Termination
- Belgium / Time / Overtime

Afficher clairement le contexte actif :

- Country
- Domain
- Topic
- Year

### 3. Knowledge Compass

Créer la zone affichant les connaissances recommandées.

Le changement de contexte doit automatiquement changer les résultats.

Pas de chatbot.
Pas besoin de barre de recherche.

### 4. Knowledge Card

Créer le composant d'affichage d'une connaissance.

Afficher :

- titre
- résumé
- type de source
- score
- pays
- domaine
- sujet
- date / validité
- provenance

Types de sources :

- PDF
- Teams
- Expert note
- Procedure

### 5. Explication du score

Afficher pourquoi une carte est recommandée.

Exemple :

Score: 92

+ Country match
+ Domain match
+ Topic match
+ Trusted source
+ Business coherence bonus

Les données seront fournies par B2.

### 6. Provenance

Permettre d'afficher :

- nom de la source
- extrait source
- URL si disponible

### 7. Affichage des conflits

Afficher visuellement lorsqu'une source est en conflit avec une autre.

Exemple :

⚠ Potential conflict detected

Official Payroll Procedure
vs
Teams message

La logique de conflit est fournie par B2.

### 8. Expert recommandé

Afficher l'expert retourné par C.

Exemple :

Recommended Expert

Sophie Lambert
Belgium Payroll Specialist
42 solved cases

### 9. Knowledge Map

Ajouter un bouton / onglet :

"Open Knowledge Map"

qui affiche le composant créé par C.

### 10. Polish final

Vérifier :

- responsive laptop
- écran 16:9
- cohérence visuelle
- états hover
- badges
- lisibilité des scores
- lisibilité des conflits

# 🟢 RÔLE B1 — DATASET / KNOWLEDGE CARDS / RELATIONS
**1 personne**

## Objectif

Construire toutes les données utilisées par l'application et déterminer
comment les Knowledge Cards sont reliées entre elles.

## Tâches

### 1. Types TypeScript

Créer :

src/types/knowledge.ts

Types nécessaires :

KnowledgeCard
WorkContext
Relation

Structure principale :

type KnowledgeCard = {
  id: string
  title: string
  summary: string

  sourceType:
    | "pdf"
    | "teams"
    | "expert_note"
    | "procedure"

  attributes: {
    country?: string[]
    domain?: string[]
    topics?: string[]
    client?: string[]
    validFrom?: string
    owner?: string
  }

  provenance: {
    sourceLabel: string
    sourceUrl?: string
    extractedAt?: string
  }

  evidence: {
    field: string
    value: string
    sourceExcerpt: string
  }[]
}

type WorkContext = {
  country: "BE" | "FR"
  domain: "Payroll" | "Time"
  topic: string
  year: number
  client?: string
}

### 2. Scénarios

Créer :

src/data/scenarios.ts

Les 3 scénarios :

1. BE / Payroll / Bonus
2. FR / Payroll / Termination
3. BE / Time / Overtime

### 3. Dataset

Créer :

src/data/knowledge-cards.ts

Créer environ 30 Knowledge Cards.

Objectif :

- minimum 6 cartes pertinentes par scénario
- quelques cartes moins pertinentes
- quelques cartes volontairement hors contexte

Les contenus peuvent être fictifs mais doivent sembler réalistes.

### 4. Types de sources

Les 4 types doivent être représentés :

- PDF
- Teams
- Expert note
- Procedure

### 5. Provenance

Chaque carte importante doit avoir :

- sourceLabel
- sourceUrl si pertinent
- evidence
- sourceExcerpt

### 6. Contradiction

Créer au moins une paire volontairement contradictoire.

Exemple :

Carte A :
"Official Belgium Bonus Procedure 2026"

Carte B :
"Teams discussion — old bonus calculation"

Les deux doivent parler du même sujet mais contenir une règle différente.

B2 utilisera cette paire pour la détection de conflit.

### 7. Relations entre Knowledge Cards

Créer :

src/lib/relations.ts

Détecter les attributs partagés :

- même pays
- même domaine
- même sujet
- même client
- référence explicite

### 8. Poids configurables

Les relations ne doivent PAS utiliser des valeurs métier codées partout
dans l'algorithme.

Prévoir une configuration du style :

relationConfig = {
  weights: {
    country: ...,
    domain: ...,
    topic: ...,
    client: ...,
    explicitReference: ...
  },

  bonuses: {
    countryDomainTopic: ...,
    clientTopic: ...
  }
}

### 9. Bonus de combinaison

Ajouter des bonus lorsque plusieurs signaux cohérents existent.

Exemples :

country + domain + topic
→ bonus

client + topic
→ bonus

### 10. API attendue

Créer idéalement :

getRelations(cardA, cardB)

qui retourne quelque chose comme :

{
  score: 72,

  reasons: [
    "same country",
    "same domain",
    "same topic",
    "country + domain + topic bonus"
  ]
}

# 🟠 RÔLE B2 — RANKING / SCORING / CONFLICTS
**1 personne**

## Objectif

Construire le moteur qui décide quelles connaissances sont les plus
pertinentes pour le contexte actuel.

Le moteur doit être :

- déterministe
- configurable
- explicable

## Tâches

### 1. Configuration du ranking

Créer par exemple :

src/config/ranking.ts

Configuration :

export const rankingConfig = {

  weights: {
    country: 20,
    domain: 20,
    topic: 30,
    temporalValidity: 10,
    trustedSource: 10,
    recency: 5
  },

  bonuses: {
    countryDomainTopic: 15,
    clientTopic: 10
  },

  penalties: {
    conflict: 15,
    uncertainty: 10
  }

}

IMPORTANT :

Les valeurs doivent pouvoir être modifiées sans changer l'algorithme.

### 2. Ranking

Créer :

src/lib/ranking.ts

Fonction principale :

rankKnowledge(cards, context)

### 3. Calcul du score

Principe :

score =
  somme(baseWeight × match × confidence)
  + bonuses
  - penalties

Prendre en compte :

- Country match
- Domain match
- Topic match
- Temporal validity
- Trusted source
- Recency
- Business coherence
- Conflict
- Uncertainty

### 4. Bonus

Ajouter des bonus pour les combinaisons fortes.

Exemple :

country + domain + topic
→ bonus

client + topic
→ bonus

### 5. Malus

Prévoir :

- conflit
- incertitude
- éventuellement source obsolète

### 6. Explication du score

Ne pas retourner uniquement :

score: 92

Retourner aussi le détail.

Exemple :

{
  card,
  score: 92,

  explanation: [
    {
      label: "Country match",
      value: 20
    },
    {
      label: "Domain match",
      value: 20
    },
    {
      label: "Topic match",
      value: 30
    },
    {
      label: "Business coherence bonus",
      value: 15
    },
    {
      label: "Recent source",
      value: 7
    }
  ]
}

A utilisera directement ces données dans l'interface.

### 7. Tri

Les résultats doivent être triés par score décroissant.

### 8. Conflits

Créer :

src/lib/conflicts.ts

Détecter ou déclarer les Knowledge Cards contradictoires.

Pour le POC, il n'est PAS nécessaire de construire un moteur NLP complexe.

Une contradiction connue dans le dataset suffit si elle est correctement
modélisée.

### 9. Tester les 3 scénarios

Vérifier :

BE / Payroll / Bonus
→ cartes Bonus BE en tête

FR / Payroll / Termination
→ cartes Termination FR en tête

BE / Time / Overtime
→ cartes Overtime BE en tête

Une source française ne doit pas arriver première dans un contexte belge
sans justification.

## API attendue

rankKnowledge(cards, context)

detectConflicts(cards)
